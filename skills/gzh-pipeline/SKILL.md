# gzh-pipeline：公众号文章总流程

把“简报 → 选题 → 初稿 → 去 AI 腔 → 排版 → 封面 → 发布前检查 → 人工发布”串成一条可恢复、可交接的流程。本技能只管流程和交付物，具体工作交给各阶段技能。

## 硬性规则（任何阶段都不能违反）

1. **只做手动发布。** 流程的终点是一个发布包，由人在公众号后台粘贴、上传、点发布。不调用任何群发、发布接口，不替人点“发表”。
2. **不扫码登录，不用非官方接口。** 不驱动已登录的公众号后台网页，不抓包调用未公开的 mp.weixin.qq.com 接口。
3. **每条事实都带出处链接。** 具体数字、日期、引语、产品能力、研究结论都要能对到一条可打开的原始链接。找不到出处就删掉或改写成明确的推断。
4. **不把含糊说法升级为确定说法。** “可能 / 据称 / 计划 / 尚未 / 约 / 超过”等限定词承载的含义要原样保留。
5. **写稿的人不审自己的稿。** 最好由不同的执行者完成 `gzh-precheck`；只有一个执行者时，必须在写完后重新读取原始资料再审，不能凭记忆判断。
6. **本流程不需要单独的大模型 key。** 所有写作、判断都由执行本技能的 agent 自己完成；脚本只做确定性的转换和检查。

## 工作目录

每篇文章一个独立目录，不同文章互不覆盖：

```
gzh/<YYYY-MM-DD>-<slug>/
├── 00-brief.md          # 输入：当天简报（原样保存，含原帖/原文链接）
├── 01-topic-card.md     # gzh-topic-pick 产出
├── 02-draft.md          # gzh-draft 产出：初稿
├── 02-claims.md         # gzh-draft 产出：论点–证据–出处对照表
├── 03-final.md          # zh-humanize 产出：终稿 Markdown
├── 03-humanize-notes.md # zh-humanize 产出：改动说明
├── 04-article.html      # gzh-format 产出：可粘贴的内联样式 HTML
├── 04-preview.html      # gzh-format 产出：本地预览页（带复制按钮）
├── 05-cover-235.png     # gzh-cover 产出：2.35:1 头图
├── 05-cover-1x1.png     # gzh-cover 产出：1:1 分享缩略图
├── 05-cover-audit.json  # gzh-cover 产出：溢出/留白自检结果
├── 06-precheck.md       # gzh-precheck 产出：通过/不通过报告
├── 06-precheck.json     # gzh-precheck 产出：机器可读结果
├── package/             # gzh-precheck 通过后才生成的手动发布包
└── status.md            # 本技能维护：各阶段状态与交接记录
```

`<slug>` 用 2–5 个英文小写单词或拼音，连字符连接。目录放在执行环境约定的共享工作区；跨执行者交接时只通过这个目录传文件。

## 阶段与交付物

| 阶段 | 技能 | 输入 | 必须交付 | 完成条件 |
|---|---|---|---|---|
| 0 建目录 | 本技能 | 简报 | `00-brief.md`、`status.md` | 简报原样保存，链接完整 |
| 1 选题 | `gzh-topic-pick` | `00-brief.md`、已发文章列表 | `01-topic-card.md` | 至少一个选题结论为“做” |
| 2 初稿 | `gzh-draft` | 选题卡 + 原始资料 | `02-draft.md`、`02-claims.md` | 对照表里没有 `unsupported` 的事实进入正文 |
| 3 去 AI 腔 | `zh-humanize` | `02-draft.md` | `03-final.md`、`03-humanize-notes.md` | 事实、限定词、链接与初稿一致 |
| 4 排版 | `gzh-format` | `03-final.md` | `04-article.html`、`04-preview.html` | 转换脚本的合规检查无错误 |
| 5 封面 | `gzh-cover` | 标题 + 风格 | `05-cover-*.png`、`05-cover-audit.json` | 自检全部通过 |
| 6 发布前检查 | `gzh-precheck` | 上面全部 | `06-precheck.*`，通过时生成 `package/` | 结论为“通过” |
| 7 人工发布 | 人 | `package/` | 无 | 人在后台确认发布 |

阶段 4 和 5 互不依赖，可以并行。

## 执行步骤

1. **建目录。** 按上面的结构建 `gzh/<日期>-<slug>/`，把简报原样存成 `00-brief.md`。简报里没有链接的条目标注“无出处”，后续阶段不得把它当事实使用。
2. **建 `status.md`。** 用 `references/handoff-format.md` 的模板，记录每个阶段的状态（`todo / doing / done / failed / blocked`）、执行者、完成时间和备注。
3. **按阶段顺序调用技能。** 每个阶段开始前先读 `status.md`，确认上游交付物存在且状态为 `done`；结束后更新状态再交接。
4. **失败就停在当前阶段。** 记录原因到 `status.md`，只重做失败的阶段，不重写已经完成的上游文件。上游确实要改时，把下游阶段全部改回 `todo`。
5. **交给人发布。** `gzh-precheck` 结论为“通过”后，向人报告：标题、摘要、发布包路径、出处数量、检查中的警告项，以及“需要在后台手动完成的操作”。到此为止，不再做任何发布动作。

## 恢复与重跑

- “继续上次”时，读取 `status.md`，从第一个不是 `done` 的阶段继续。
- 同一选题要重写时，新建目录（slug 加 `-v2`），旧目录保留作记录。
- 发布后如需更正，另起一篇或在后台手动编辑，本流程不改已发布内容。
