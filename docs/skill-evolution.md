# 技能怎么进化：待审改动与教训记录

技能会在实际使用中暴露问题。这份约定规定：谁可以提改动、改动怎么提、什么时候才能合入，以及每个执行者怎么记录教训。目标是让技能越用越好，又不让它变成事故流水账，也不让任何执行者绕过人自己改技能。

> 做法借鉴 Hermes Agent 技能文档中的“记教训，不记日志”和写入审批门（skills.write_approval），本仓库只借思路，未收录其代码。见 CREDITS.md。

## 一、谁能改技能

- 任何执行者（写稿、选题、检查、调研等角色）都**不能直接修改** `skills/` 或技能库里的技能。
- 想改，只能提交一份**待审改动**（见第二节）。
- 只有人批准后，由流程负责人把改动合入本仓库，跑完 `evals/run_checks.py`，再同步到技能库。被拒绝的改动不合入，也不换个说法重提，除非有新证据。

## 二、待审改动

放在团队约定的待审目录里（共享电脑上是 `/workspace/trainer/pending/`），一个改动一个文件，文件名用 `<技能名>-<短描述>.md`。内容：

```markdown
---
target: <技能名>/<文件，例如 SKILL.md 或 references/patterns.md>
proposer: <提议的角色>
status: pending          # pending / approved / rejected / merged
---

## 理由（一行）

## 改动
<统一 diff，或“替换为”的完整新文字；新增内容写明放在哪一步之后>

## 例子
- 改前：<按现在的技能会怎么做 / 产出什么>
- 改后：<按新规则会怎么做 / 产出什么>
```

要求：

- 每条改动只解决一个问题，附改前、改后各一个例子。
- 拟写入技能的文字按第三节的格式写：规则 + 原因 + 影响哪一步。
- 每周最多提 3 条，挑影响最大的；人审不过来的改动等于没有改动。
- 提交前可以先自查：`python evals/check_skill_change.py --scan <待审改动文件>`。

## 三、教训记录（lessons.md）

每个执行者在自己的工作目录里维护一份 `lessons.md`，任务结束后有值得记的教训就补一条。格式：

```markdown
- **规则**：<一句可推广的规则>
  - 原因：<一句话说明机制，为什么不这样会出问题>
  - 影响：<哪个技能的哪一步>
```

例子：

```markdown
- **规则**：出处链接和它支撑的句子放在同一段，不集中到文末。
  - 原因：排版会把文末链接转成参考资料编号，读者对不上是哪句话的出处。
  - 影响：gzh-draft 步骤 4
```

不写进去的东西：

- 事故经过（“那次稿子发出去才发现……”）；
- 日期、时刻、issue/PR 编号；
- 聊天原话、对话记录、“某某说”；
- 具体机器人或账号的名字（技能要对任何执行者都适用）。

同一条规则只记一次；已有的规则有新情况，就在原条目上改，不另起一条。

定期（建议每周）由一个角色汇总各执行者的 `lessons.md`，挑出最多 3 条值得进技能的，按第二节写成待审改动。

## 四、合入前检查

合入前在仓库根目录运行：

```bash
.venv/bin/python evals/check_skill_change.py          # 工作区 vs HEAD
.venv/bin/python evals/run_checks.py                  # 全部回归检查（已包含上一条）
```

`check_skill_change.py` 检查三件事：

| 检查 | 默认阈值（可用参数调整） | 出问题怎么办 |
|---|---|---|
| SKILL.md 正文过长 | 160 行或 6000 字（`--max-lines`、`--max-chars`） | 常驻规则留在 SKILL.md，细节移到 `references/` 里按主题命名的已有文件 |
| 参考文件膨胀 | 一次最多新增 1 个参考文件，每个技能最多 8 个；单个文件增长超过 1.5 倍且多于 800 字（`--max-new-files`、`--max-files`、`--max-growth`、`--min-growth-chars`） | 补进已有文件，删掉重复内容；不要每次新建一个文件 |
| 混进日期或聊天记录 | 新增行里的日期、时刻、“用户说”、对话标记、机器人名、issue/PR 编号（出处后的“YYYY-MM 查阅”除外；代码块内不查） | 改写成“规则 + 原因 + 影响哪一步” |

检查通过不代表改动一定好。合入前还要用改动附带的例子，加上 `evals/` 里的相关用例，对比改前、改后的表现。
